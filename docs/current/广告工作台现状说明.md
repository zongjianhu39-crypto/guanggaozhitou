# 广告工作台现状说明

最后更新：2026-05-08

本文档用于给后续人工维护、Codex、Cline、Qoder 等代码助手快速理解当前广告工作台。后续改代码前，建议先读本文档，再读对应模块说明和实际代码。

注意：本文档是系统现状说明，不是数据库事实源。涉及真实表名、字段名、接口返回结构时，以 Supabase migration、Edge Function 代码和线上数据库结构为准。

## 1. 现在网站有哪些页面

当前广告工作台的核心页面主要有 5 个：

| 页面 | 页面名称 | 主要前端文件 | 主要后端接口 |
| --- | --- | --- | --- |
| `supabase-dashboard.html` | 数据看板 | `dashboard.js`、`assets/js/dashboard-*.js` | `dashboard-data` |
| `plan-dashboard.html` | 计划拆解 | `assets/js/plan-dashboard-*.js` | `plan-dashboard-summary` |
| `genbi.html` | GenBI 智能问数 | `assets/js/genbi-page.js` | `genbi-query` |

| `prompt-admin.html` | Prompt 管理 | `prompt-admin.js` | `ai-prompt-admin`、`ai-prompts` |

同时，项目里还有一些相关页面，虽然不是本次说明的主对象，但改导航、权限、发布清单时容易被影响：

| 页面 | 说明 |

## 2. 每个页面解决什么业务问题

### 2.1 数据看板：`supabase-dashboard.html`

数据看板是当前投放分析的主页面，核心目标是让业务人员看清广告投放表现。

它主要解决：

- 看投放大盘：花费、成交、ROI、广告收入、盈亏平衡 ROI 等核心指标。
- 看人群维度：按人群分层、人群名称等维度观察消耗、成交和 ROI。
- 看计划 / 单品维度：区分直播间投放、单品投放等计划类型，支持单品相关指标。
- 看时间范围：支持按日期范围查询，并对日、周、月等聚合口径做展示。
- 触发 AI 分析：部分分析能力会读取看板数据并生成洞察报告。

主要风险点：

- `dashboard-data` 返回结构一变，前端渲染、导出、AI 分析都可能受影响。
- 人群分类、计划分类依赖 `assets/data/dashboard-spec.json` 和后端共享规则。
- 汇总表和原始表之间存在 fallback 逻辑，改动时要确认是否仍能回退。

### 2.2 计划拆解：`plan-dashboard.html`

计划拆解页面用于看 618、月度节奏、日度预算和实际消耗之间的关系。

它主要解决：

- 看月度 / 活动节奏：按日期展示计划金额、实际花费、活动覆盖和备注。
- 拆解日度计划：维护万相台计划金额、有客代投计划金额等日级计划。
- 对比实际花费：从实际投放数据表中汇总万相台、有客代投花费。
- 看 2025 年参考：展示上一年同月同日投放参考值。
- 维护活动和备注：支持活动新增、编辑、删除，以及单日 / 月度备注。

当前文档事实源：

- 模块说明：`docs/current/plan-dashboard-module.md`
- 前端入口：`assets/js/plan-dashboard-page.js`
- 后端入口：`supabase/functions/plan-dashboard-summary/index.ts`
- 核心计算：`supabase/functions/_shared/plan-dashboard-core.ts`

主要风险点：

- 日期字段和日期格式非常敏感，`plan_date`、`date`、直播日期等字段不要随意混用。
- 计划表、活动表、实际花费表来源不同，字段缺失时要保证页面能降级展示。
- 行内编辑、保存单日、保存全部容易和前端状态同步互相影响。

### 2.3 GenBI 智能问数：`genbi.html`

GenBI 是规则问数和自然语言问数入口，目标是让业务用问题获取结构化答案。

它主要解决：

- 用自然语言问投放数据，例如 ROI、人群、单品、日期范围等问题。
- 结合规则和语义配置，把问题映射到稳定的数据口径。
- 调用模型生成解释性答案，同时尽量保持指标和数据可追溯。
- 通过 RAG / 规则配置引用历史报告、指标说明、业务规则。

当前相关代码：

- 前端：`assets/js/genbi-page.js`
- 问数函数：`supabase/functions/genbi-query/index.ts`
- 规则解析：`supabase/functions/_shared/genbi-rule-resolver.ts`
- 语义配置：`assets/data/genbi-semantic.json`、`supabase/functions/_shared/genbi-semantic.ts`
- RAG：`supabase/functions/_shared/genbi-rag.ts`

主要风险点：

- GenBI 同时依赖数据接口、规则、语义配置和模型调用，任何一层变动都可能导致问数不准。
- 指标口径不能只改前端展示，必须同步规则、文档和后端语义。
- 模型输出需要过滤和约束，避免把思考过程、无依据结论或错误字段展示给用户。

### 2.4 指标与规则台：`metric-rules.html`

指标与规则台是给业务和开发查看指标口径、维度规则的页面。

它主要解决：

- 展示投放指标公式，例如 ROI、广告收入、盈亏平衡 ROI 等。
- 展示计划分类规则，例如单品投放、直播间投放。
- 展示人群分层规则，例如纯黑盒、灰盒、老客、兴趣新客、新客等。
- 帮助改代码前确认“该字段能不能直接 sum”“该比率是否必须重算”。

当前相关代码：

- 前端：`assets/js/metric-rules-page.js`
- 机器可读规则：`assets/data/dashboard-spec.json`
- 人类说明文档：`docs/current/报表字段及关系-标准文档.md`
- 后端规则加载：`supabase/functions/_shared/dashboard-spec.ts`

主要风险点：

- 文档、JSON 规则和后端加载逻辑必须保持一致。
- 比率指标不能直接加总或平均，必须按公式基于汇总后的分子分母重算。
- 人群分层优先级会影响结果，新增关键词时要确认互斥关系。

### 2.5 Prompt 管理：`prompt-admin.html`

Prompt 管理台用于维护 AI 分析和问数相关的 Prompt 模板。

它主要解决：

- 查看、编辑、发布 Prompt 模板。
- 管理草稿、版本、回滚等 Prompt 生命周期。
- 让 AI 分析能力不需要每次改代码才能调整提示词。

当前相关代码：

- 前端：`prompt-admin.js`
- 后端管理接口：`supabase/functions/ai-prompt-admin/index.ts`
- 旧版 Prompt 查询：`supabase/functions/ai-prompts/index.ts`
- 共享存储逻辑：`supabase/functions/_shared/prompt-store.ts`
- 权限逻辑：`supabase/functions/_shared/prompt-admin-auth.ts`

主要风险点：

- Prompt 管理涉及权限，不要绕过登录态或管理 token 校验。
- Prompt 结构一变，AI 分析、GenBI、报告生成可能同时受影响。
- 发布 / 回滚逻辑要保留版本记录，避免误覆盖线上可用模板。

## 3. 数据从哪里来

当前系统的数据来源可以分为 5 类。

### 3.1 阿里妈妈 / 超级直播投放数据

用途：

- 数据看板的广告投放指标。
- 人群维度、计划维度、单品维度分析。
- GenBI 问数的数据底座之一。

相关表和路由：

- 2025 年使用 `super_live_2025`。
- 2026 年及以后按月分表，类似 `super_live_202601`。
- 表路由逻辑在 `supabase/functions/_shared/table-routes.ts`。

典型字段：

- 日期、计划 ID、计划名字、人群名字。
- 花费、观看次数、展现量、总成交金额、总成交笔数、直接成交金额等。

### 3.2 淘宝直播数据看板

用途：

- 补充直播间整体观看、成交、退款、加购等数据。
- 用于跨报表派生指标，例如广告成交占比、广告收入、盈亏平衡 ROI。

典型字段：

- 日期 / 直播日期。
- 观看人数、观看次数、成交人数、成交笔数、成交金额、退款金额等。

### 3.3 本地 CSV / 手工导入数据

用途：

- 承接平台导出的原始报表。
- 经过清洗后进入 Supabase 原始表或聚合表。

注意事项：

- CSV 字段名可能带有“（元）”等后缀，清洗后字段名可能会被标准化。
- 文件导入时要确认日期列、金额列、中文列名是否被正确识别。
- 如果字段名变化，前端不一定直接报错，但指标可能变成 0 或 null。

### 3.4 Supabase 原始表

用途：

- 保存从平台或本地文件导入的明细数据。
- 当聚合表不可用或参数要求 raw 查询时，`dashboard-data` 会回退读取原始表。

当前重要原始表包括：

| 表 | 用途 |
| --- | --- |
| `super_live_2025`、`super_live_YYYYMM` | 超级直播 / 阿里妈妈投放明细 |
| `financial_2026` | 财务口径收入、佣金、成本、毛利等 |
| `short_live_link_2026` | 计划拆解中的万相台实际花费来源之一 |
| `live_ad_agent_2026` | 计划拆解中的有客代投实际花费来源之一 |
| `ad_plans` | 日级计划金额 |
| `ad_plan_activities` | 活动时间轴 |
| `ad_plan_month_notes` | 月度 / 节奏备注 |
| `ai_reports` | AI 洞察报告 |
| `genbi_rule_configs` | GenBI 动态规则配置 |
| `genbi_query_events` | GenBI 问数事件记录 |

### 3.5 Supabase 聚合表

用途：

- 提升看板查询速度。
- 给数据看板提供日级聚合后的 ads、crowd、single product 数据。

当前重要聚合表包括：

| 表 | 用途 |
| --- | --- |
| `dashboard_ads_daily_summary` | 广告投放日级汇总 |
| `dashboard_crowd_daily_summary` | 人群维度日级汇总 |
| `dashboard_single_product_daily_summary` | 单品维度日级汇总 |

注意事项：

- 聚合表字段必须和 `supabase/functions/_shared/dashboard-payload.ts` 读取字段保持一致。
- 聚合表缺数据时，`dashboard-data` 可能会 fallback 到 raw 查询，但性能和结果口径要单独确认。
- 刷新聚合表后，要用相同日期范围对比 raw 和 summary 是否一致。

## 4. 哪些地方最容易改崩

### 4.1 日期字段

最容易出问题的是日期字段不统一。

常见风险：

- `日期`、`date`、`直播日期`、`plan_date` 被混用。
- 字符串日期、时间戳、带时区日期格式互相转换后错一天。
- 前端选择日期范围是闭区间，但后端查询写成半开区间或反过来。

改动建议：

- 改任何日期逻辑前，先搜索对应接口的 `start`、`end`、`date`、`plan_date`。
- 至少用一个固定日期范围做回归，例如 release check 当前使用的 `2026-04-07`。

### 4.2 Edge Function

Edge Function 是前后端之间最关键的边界。

常见风险：

- 函数部署漏了，本地代码和线上函数不一致。
- CORS header、鉴权 header 或错误响应格式被改坏。
- 返回字段改名后，前端还在读旧字段。
- 共享模块 `_shared` 改动会影响多个函数。

重点函数：

- `dashboard-data`
- `plan-dashboard-summary`
- `genbi-query`
- `genbi-rule-admin`
- `ai-prompt-admin`
- `ai-analysis`
- `audience-repository`

### 4.3 聚合表刷新

数据看板优先使用聚合表，聚合表一旦没刷新或字段不一致，就会出现“页面能打开但数据不对”的问题。

常见风险：

- 原始表有新数据，但聚合表没有同步。
- 聚合表刷新逻辑变了，但 `dashboard-payload.ts` 没同步。
- 某个维度在 raw 查询里有，在 summary 查询里丢了。
- 人群维度以前走 summary，后来强制 raw 后口径变动。

检查建议：

- 同一日期范围分别检查 ads、crowd、single 的来源是 `summary` 还是 `raw`。
- 聚合刷新后检查 source row count 是否合理。

### 4.4 指标公式

指标公式是最容易“看起来正常、实际错了”的地方。

常见风险：

- ROI、转化率、退款率等比率被直接 sum 或平均。
- 广告收入和业务口径收入去折损混用。
- 不可计算值被强行写成 0，导致汇总结果偏低。
- 前端展示公式、后端计算公式、GenBI 解释公式不一致。

改动原则：

- 先改 `docs/current/报表字段及关系-标准文档.md`。
- 再改 `assets/data/dashboard-spec.json`。
- 涉及后端时同步 `dashboard-spec.ts`、`dashboard-payload.ts`、GenBI 语义文件。

### 4.5 CORS、权限和登录态

当前页面使用 Supabase Edge Function、飞书登录和前端静态站组合，权限链路不能随意改。

常见风险：

- CSP / CORS 放开或收紧后，线上静态站无法请求 Supabase。
- Prompt 管理、规则管理等后台页绕过权限。
- 本地调试能访问，线上域名不能访问。
- Supabase anon key / publishable key 配置缺失。

重点文件：

- `assets/js/config.js`
- `assets/js/auth-helpers.js`
- `auth.js`
- `supabase/functions/_shared/request-auth.ts`
- `supabase/functions/_shared/prompt-admin-auth.ts`

### 4.6 前后端字段不一致

这是当前复杂度最高的风险之一。

常见风险：

- 后端字段从 snake_case 改成 camelCase，前端没同步。
- 前端新增展示列，但接口没有返回。
- 聚合表新增字段，raw fallback 没有同名字段。
- GenBI 的语义字段、业务文档字段、数据库字段不是同一套名字。

改动建议：

- 改接口返回结构时，必须同时搜索前端读取点。
- 尽量新增字段而不是直接改旧字段名。
- release check 里已有合约测试时，优先更新合约测试再改实现。

## 5. 每次上线前必须检查什么

### 5.1 本地发布前检查

每次上线前先执行：

```bash
npm run check:release
```

这个命令用于确认本地代码具备发布条件，当前包括：

- 静态文件完整性检查。
- 密钥扫描。
- GenBI 回归测试。
- GenBI 合约测试。
- GenBI 动态规则测试。
- 计划看板回归测试。
- 计划看板合约测试。
- 计划看板 UI 检查。
- 安全合约测试。

详细说明见：

- `docs/current/release-check-guide.md`
- `tools/checks/release-check.config.json`

### 5.2 Edge Function 是否部署

如果改了 `supabase/functions/` 下的文件，不能只上传静态文件。

必须确认对应 Edge Function 已部署：

- 改 `dashboard-data`：确认数据看板接口返回新逻辑。
- 改 `plan-dashboard-summary`：确认计划拆解页面数据和保存功能正常。
- 改 `genbi-query`：确认 GenBI 能问数并返回答案。
- 改 `ai-prompt-admin`：确认 Prompt 管理能读取、保存、发布。
- 改 `_shared`：确认所有引用它的函数都完成部署和回归。

### 5.3 静态文件是否上传

如果改了 HTML、CSS、前端 JS 或 `assets/data/*.json`，必须确认静态文件已经上传到线上站点。

重点确认：

- HTML 页面上传。
- 对应 `assets/js/*.js` 上传。
- 对应 `assets/css/*.css` 上传。
- `assets/data/dashboard-spec.json`、`assets/data/genbi-semantic.json` 上传。
- 浏览器没有继续使用旧缓存。

### 5.4 关键页面是否能打开

上线后至少打开以下页面：

- `supabase-dashboard.html`
- `plan-dashboard.html`
- `genbi.html`
- `metric-rules.html`
- `prompt-admin.html`

如果本次改动涉及相关模块，还要打开：

- `audience-repository.html`
- `genbi-rule-admin.html`
- `insights.html`
- `budget-scorecard.html`

### 5.5 核心接口是否返回数据

上线后要确认核心接口不是只返回 200，而是真的有业务数据。

重点检查：

- `dashboard-data`：指定日期范围后，ads、crowd、single 至少能返回合理结构。
- `plan-dashboard-summary`：指定月份 / 日期范围后，计划、实际、活动、备注能返回。
- `genbi-query`：问一个固定问题，确认答案可读且没有字段错误。
- `ai-prompt-admin`：确认管理页能读取当前 Prompt。
- `genbi-rule-admin`：确认规则列表能读取。

### 5.6 部署后线上冒烟检查

部署完成后执行：

```bash
npm run check:release:online
```

这个命令会在本地 release check 基础上增加线上关键页面和接口检查。

## 6. 后续让代码助手改代码时的使用方式

建议给 Codex、Cline、Qoder 的第一句话包含：

> 先阅读 `docs/current/广告工作台现状说明.md`，再阅读本次要改模块对应的源码和测试。不要直接重构全站。涉及指标、日期、Edge Function、聚合表、权限和前后端字段时，先说明风险点和验证方式。

不同需求对应的入口：

| 需求 | 优先阅读 |
| --- | --- |
| 改数据看板 | `supabase-dashboard.html`、`assets/js/dashboard-*.js`、`supabase/functions/dashboard-data/index.ts`、`supabase/functions/_shared/dashboard-payload.ts` |
| 改计划拆解 | `docs/current/plan-dashboard-module.md`、`plan-dashboard.html`、`assets/js/plan-dashboard-*.js`、`supabase/functions/plan-dashboard-summary/index.ts` |
| 改 GenBI | `genbi.html`、`assets/js/genbi-page.js`、`supabase/functions/genbi-query/index.ts`、`supabase/functions/_shared/genbi-*.ts` |
| 改指标规则 | `docs/current/报表字段及关系-标准文档.md`、`assets/data/dashboard-spec.json`、`metric-rules.html` |
| 改 Prompt | `prompt-admin.html`、`prompt-admin.js`、`supabase/functions/ai-prompt-admin/index.ts` |
| 改登录 / 权限 | `auth.js`、`assets/js/auth-helpers.js`、`auth/`、`supabase/functions/_shared/request-auth.ts` |

改动完成后的最低验证要求：

1. 运行 `npm run check:release`。
2. 打开被改页面，确认页面能加载。
3. 用一个固定日期范围验证核心数据。
4. 如果改了 Edge Function，确认线上函数已部署。
5. 如果改了静态文件，确认线上静态资源已上传。
